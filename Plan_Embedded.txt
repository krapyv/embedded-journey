Week 16: MCP2515 (SPI) — Configuration, Loopback TX/RX, Filter Setup ✅

Before touching a register: read the MCP2515 datasheet sections 5 (bit timing), 10 (modes of operation), and 12 (SPI interface) in full. The architecture is fundamentally different from what "CAN peripheral" meant in the original plan — you're not configuring an on-chip peripheral, you're driving an external controller over SPI, the same way you just did with the EEPROM. Your spi_transfer() from Week 15 is directly reusable here — same CS/mode-0 mechanics, different device on the bus.

One extra piece in your setup the original plan didn't have: the TXS0108E level shifter. This tells you your MCP2515 module is almost certainly a 5V-logic board (common on the cheap MCP2515+TJA1050 combo boards), and you're bridging it to your 3.3V STM32 SPI lines. That shifter is auto-direction-sensing, not a simple buffer — it infers signal direction from edge timing and relies on pull resistors and bus capacitance. At higher SPI clocks this can distort edges. Put your logic analyzer on both sides of the shifter before you assume a communication failure is a register misconfiguration.

Theory to understand before coding:

Bit timing is now derived from the MCP2515's own oscillator, not STM32 APB1. Find your module's crystal frequency (commonly 8 MHz or 16 MHz — check the can on the board or measure it) and compute BRP, PRSEG, PHSEG1, PHSEG2, SJW from that, same discipline as before but a different clock source and a different register set (CNF1/CNF2/CNF3, not CAN_BTR).
Mode switching: CANCTRL REQOP[2:0] bits select Configuration/Normal/Sleep/Listen-Only/Loopback mode. A mode request must be confirmed by reading CANSTAT's OPMOD field back — same "request, then poll for confirmation" pattern as bxCAN's INRQ/INAK, just different register names.
SPI command set is the real new material this week: RESET, READ, WRITE, READ RX BUFFER, LOAD TX BUFFER, RTS (request-to-send), READ STATUS, BIT MODIFY. This is a richer instruction set than the EEPROM's four opcodes — BIT MODIFY in particular (mask byte + data byte) is worth understanding before you use it, since several status/control registers are only safely modifiable that way per the datasheet.

Register sequence to implement:

Hardware reset — either drive the RESET pin low, or send the SPI RESET instruction. Either puts the device in Configuration mode.
Confirm Configuration mode via CANSTAT.
Configure CNF1/CNF2/CNF3 for your target bitrate against your module's actual oscillator frequency.
Configure at least one filter/mask pair (RXF0–RXF5, RXM0/RXM1) — these registers only read/write correctly in Configuration mode, same restriction as CAN_FMR on bxCAN.
Set CANCTRL REQOP to Loopback mode, confirm via CANSTAT.

TX sequence: load TXBnSIDH/SIDL (and EID if extended) for ID, TXBnDLC for length, TXBnDn for data — either via WRITE to the buffer address or the faster LOAD TX BUFFER instruction — then trigger transmission via the RTS instruction or by setting TXREQ directly.

RX sequence: poll CANINTF RXnIF (or use READ STATUS for a faster combined check), then read RXBnSIDH/SIDL/DLC/Dn — either via READ or the faster READ RX BUFFER instruction, which auto-clears the RXnIF flag on CS rise.

Done bar: same as before — transmit a frame in loopback mode, receive it back, print ID and data over UART.

Week 17: MCP2515 — Interrupt-Driven, Error Handling, Two-Node Test ✅

The interrupt model is structurally different from bxCAN's three separate vector table entries. The MCP2515 has a single active-low INT pin — you wire that to one EXTI line on the STM32. Inside that one ISR, you read CANINTF to determine which condition fired (RX0IF, RX1IF, TX0IF/TX1IF/TX2IF, ERRIF, MERRF, WAKIF) — the demultiplexing bxCAN did in hardware across three vectors, you now do in software against one register.

Error handling — conceptually the same idea as bxCAN (error-active → error-passive → bus-off), but the register is EFLG, not CAN_ESR, with its own bit layout for the error flags, and separate TEC/REC counter registers rather than one combined register. Read the EFLG bit definitions before assuming bxCAN's exact thresholds and field positions carry over.

Done bar: same as before — interrupt-driven TX and RX working, error/status handler correctly reads and clears conditions via the SPI interface, and (if you have two boards, or the level shifter and MCP2515 support it) a genuine two-node bus test rather than loopback.

Week 19: Low Power Modes ✅

Read RM0383 Chapter 5 (power modes) in full before coding.

Three modes to implement and measure:

Sleep mode:

__WFI() instruction — CPU halts, peripherals continue
SysTick interrupt wakes the CPU every 1ms
Measure: current draw with multimeter or bench supply in sleep vs active

Stop mode:

PWR_CR PDDS=0, LPDS=0/1 for main/low-power regulator
SCB_SCR SLEEPDEEP bit set
All clocks stopped except LSI/LSE
Wakeup via EXTI line (wire a button to PA0, configure EXTI0)
After wakeup: HSI restarts, you must reconfigure PLL if used
Measure: current drop vs sleep mode

Standby mode:

PWR_CR PDDS=1
SRAM contents lost — only backup registers survive
Wakeup via WKUP pin (PA0) or RTC alarm
Measure: lowest current draw

Done bar: demonstrate all three modes via UART menu — press 1 for sleep, 2 for stop, 3 for standby. Each mode wakes on button press and prints confirmation over UART.

Week 20: Bootloader

This is the most architecturally complex week in Phase 3. Read the linker script ✅ and startup file ✅ before writing a single line.

Concepts to understand first:

Vector table relocation — SCB_VTOR register, why the application's vector table must be at a known offset ✅
Flash sector layout on STM32F411 — Sector 0 is bootloader (0x08000000), Sector 1 is application (0x08004000 or 0x08008000)
Stack pointer validation — first word of application vector table must be a valid SRAM address before jumping
Bare-bones HardFault handler (register dump on fault, halt).
Bootloader sequence:

On reset, bootloader runs from Sector 0
Check a flag in backup SRAM or a GPIO pin — should we stay in bootloader or jump to application?
If jumping: read application stack pointer from *(uint32_t*)APP_START_ADDR, write to MSP, read reset handler address from *(uint32_t*)(APP_START_ADDR + 4), jump
If staying: receive new firmware over UART (XMODEM or simple raw binary protocol), write to Flash using FLASH_CR unlock sequence, sector erase, programming

Flash write sequence:

Unlock FLASH_CR with KEY1 (0x45670123) and KEY2 (0xCDEF89AB)
Erase target sector — set SER bit, SNB field, STRT bit, wait for BSY to clear
Program word by word — set PG bit, write to Flash address, wait for BSY

Done bar: bootloader receives a binary over UART, writes it to Sector 1, validates the vector table, and jumps to the application. Application blinks an LED and prints "App running" over UART.

Week 21: Integration Project — CAN Sensor Node ✅

This is not a tutorial week. You build a complete system from everything in Phase 3.

Project: BMP280 reads temperature and pressure over I2C. The STM32 packages the readings into a CAN frame and broadcasts on the bus every 500ms. A second node (or loopback) receives the frame and prints the decoded values over UART.

This is a real automotive pattern. A sensor ECU reads a physical quantity and broadcasts it on the bus. Any other ECU on the bus can consume it.

CAN frame design:

ID: 0x100 for temperature, 0x101 for pressure (or pack both into one 8-byte frame)
DLC: 4 bytes per value
Data: raw int32_t / uint32_t from BMP280 compensation functions

Integration requirements:

BMP280 state machine running on I2C interrupt driver (your existing code)
SPI transaction to the MCP2515 triggered from an interrupt
UART output for debugging
SysTick for 500ms broadcast timer

Done bar: stable temperature and pressure values broadcast on CAN bus every 500ms, decoded and printed on receiving end. No bus-off events after 60 seconds of continuous operation.

(NOTE: in the future project refactoring, move from the CANable as a second node to the second STM32F411)

This is a very smart question to ask at the start of a long-term plan. The direct answer is yes, the landscape will shift, but the core fundamentals you are about to learn are your shield against obsolescence.

Here is what will change in the next two years, what will stay the same, and how your 24-month plan prepares you for both.

🧱 The Unshakeable Core: What Will NOT Change
The "basics" are not going anywhere. They are the physics of embedded systems. Your first 12-18 months are an investment in the skills that will be more valuable, not less, as systems get complex.

The C/C++ Foundation: Every single university module for 2026/27 still teaches C and C++ as the non-negotiable entry point for embedded systems . You cannot build a safe house on a weak foundation. New tools build on top of this, they don't replace it.

Core Peripherals (I2C, SPI, UART, CAN): These are the protocols that sensors, actuators, and ECUs use to talk to each other . The menus might change, but the dishes (I2C, SPI, etc.) will remain the same.

Real-Time Operating Systems (RTOS) & State Machines: As cars become centralized, managing multiple tasks with guaranteed timing is the core challenge . This is why you are learning FreeRTOS and state machines.

Debugging & Hardware Knowledge: The need to use logic analyzers, read datasheets, and understand a schematic will never be automated away. AI can write code, but it cannot probe a physical pin to see why it's not toggling .

🚀 The Major Shifts: What WILL Change (and Why You're Ready)
The industry is undergoing a massive transformation. By mastering the fundamentals, you position yourself to ride this wave, not be crushed by it.

1. The Rise of "Software-Defined Vehicles" (SDV)
The trend is moving from 100 small computers (ECUs) to a few powerful, centralized ones . This is where the complexity explodes. Synopsys predicts that by 2027, new cars will have over 600 million lines of code—double what they have today .

How your plan helps: Your plan directly targets this. The shift to centralization requires exactly the skills you are building: C++ for Adaptive AUTOSAR, RTOS for task management, and system-level thinking.

2. AI is Becoming a Development Tool (Not a Replacement)
New startups like H2LooP are building AI tools specifically to handle the grunt work of embedded engineering, like generating test cases or checking compliance with safety standards like ISO 26262 .

How your plan helps: You are learning the rules (MISRA, AUTOSAR) that these AI tools must follow. The engineer of the future won't be the one who resists AI, but the one who knows the domain well enough to supervise the AI's output and catch its mistakes.

3. The Virtualization of Hardware (Digital Twins)
The old way was to wait for the physical chip to arrive before coding. The new way is to use a "virtual development kit" (VDK) – a digital twin of the chip – to start coding 12 months earlier .

How your plan helps: This is a workflow change, not a fundamental skill change. You will still be writing C++ for an ARM core; you'll just be doing it on a laptop simulating the car, rather than on the physical hardware. Your deep knowledge of the hardware (Phase 3) will make you highly effective in a virtual environment.

🎯 How to Update Your Learning Plan for the Future
Your plan is already 90% there. Here are two small tweaks to future-proof it even more.

Double Down on C++ (You already are): The move to centralized, software-defined vehicles is a move toward complex C++ application layers. Your decision to add a dedicated C++ phase is the single most important thing you can do .

Look for "Virtual" Opportunities: In Months 21-24, after you've mastered the physical STM32, seek out introductions to Virtual Development Kits (VDKs). Understanding how to develop and test on a virtual ECU is a skill that will be in high demand by 2028 .

💡 The Bottom Line
You will not be "learning the wrong thing." By mastering C, C++, RTOS, and CAN, you are learning the vocabulary and grammar of this industry.

The industry will invent new dialects (new tools, new AI assistants), but you will be fluent enough to learn them in a week. The engineers who struggle will be those who skip the fundamentals and try to learn only the latest trendy framework.

Stay the course. Your plan is built for exactly this future.
